# Configuration

## Project settings

`dev-loop.json` holds `version` and `harnesses`, and optional keys:

- `commands`: the project's own command for a step. Keys: `gate`, `stack_up`, `stack_reset`, `acceptance`, `acceptance_failed`, `release_prepare`, `release_check`, `release_verify` (the last three are read by `/release`, see `reference/release.md`). Each value is a non-empty string. A missing key falls back to `scripts/gate.sh`, `docker compose` and the stack's test runner. `check_setup.py` fails on any other key.
- `merge`: `auto` (the default) or `human`. With `auto`, Stage 7 merges a Track S or M pull request after green CI and the review wave, when it is a two-way door with a small blast radius. A one-way door or a Track L pull request waits for you. With `human`, every pull request waits for you. Stage 7 runs `devloop.py merge-check` to decide, and `merge_human_paths` in `dev-loop.json` lists path patterns whose changes always wait for you.
- `walled_skills`: the project skills `implementer` can call: a list of names under `.claude/skills/`, read from `main`. The skill must have no `context: fork`, shell line or `hooks` key, and the feature worktree and the main checkout must equal `main`: a stale checkout gives a denial until it is rebased or pulled. No effect on Codex.
- `source_dirs`: the folders that hold your implementation, which `spec-tester` cannot read: a list of paths from the repo root, each ending in `/` (`["internal/", "cmd/"]`), read from `main`, never from the checkout. An entry matches from the repo root only. A repo with no key keeps the wall on `src/ app/ backend/ frontend/`. `[]` is valid and walls nothing. A key is a one-way door: it joins the `merge-check` trusted keys, so a change waits for you. Files at the repo root cannot be walled, and no entry may equal or lie under `tests/acceptance/`. When the key is missing, Stage 0 reads the `source_dirs missing` line of `check_setup.py`, proposes the entries from its folder list, and writes the key once you confirm. `init` and `upgrade` never write it. The wall decision is `devloop.py source-wall` (`reference/cli/source-wall.md`). No effect on the implementer wall.
- `security_audit`: `{"images": {"<name>": "<image>"}}`, the container images the release audit sandbox may start (name: lower case letters, digits, `_` and `-`). Pull each image first; `check_setup.py` reports a stopped Docker engine or a missing image. No `images` key (or an empty one) gives `no-images`, a failing `docker info` gives `no-engine`: `/release-audit` stops with `no-sandbox`. An image that is set but not pulled passes the plan and fails later, in `sandbox-run.py`. `/release-audit --no-sandbox` drops that check only: with no images or no engine the run is source-only, else step 3 still uses the sandbox. Add `Security Audit/` (and `security-audit/`, for notes from 2.x) to the notes folder `.gitignore`: the run folders (`Security Audit/Run <N>/`) hold exploit details, and a notes git plugin must not commit them.
- `second_review`: a JSON boolean, the project lock, read from `main` only, off when absent. `init` and `upgrade` never write it. Each person also opts in, in `dev-loop.local.json` of the main worktree: `second_review` is `false`, or an object keyed by `codex` and `claude`, each `false` or `{"model": "<model>", "effort": "<effort>"}` (both optional). When the project key is true, Shaping (Stage 1) asks about the reviewer of the current harness only and writes that one key. An unanswered question leaves the file as it is, so a later Shaping asks again. Both locks must be on, else the Stage 6 run gives `skipped` (`project-off`, `not-chosen`, `user-off`, `no-main-ref`). A project key that is not a boolean, a bad local shape or a tracked `dev-loop.local.json` gives `failed` `bad-config`; the other outcomes are in the reference. The reviewer is the other family's CLI: `codex` in a Claude Code session, `claude` in a Codex one. Full contract: `reference/cli/second-review.md`.

## Notes folder

Feature folders (`Features/<YYYYMMDD> <Title>/` with `Framing.md`, `Spec.md`, `Plan.md`) live in a notes folder, any local folder. `skill/scripts/notes_path.py` finds it, first match wins:

1. `DEV_LOOP_NOTES` environment variable.
2. `notes` in `dev-loop.local.json` in the main worktree only; a feature worktree's own copy is never read. A file with no `notes` key (only `second_review`, for example) goes on to 3. This file is gitignored: each person and each machine sets its own path.
3. `notes` in the committed `dev-loop.json`, read from `main` (`origin/main`, else `main`): a key committed only on a branch is ignored. For a team that keeps its notes in the repository (for example `docs/dev-loop`).

A path is absolute, starts with `~`, or is relative to the repository root. The folder must exist. `init --notes=<path>` writes the local file.
