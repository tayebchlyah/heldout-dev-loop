# seal-check

- `seal-check [--uncommitted]`: checks the seal commits in `<base>..HEAD` (`<base>`: `git merge-base HEAD origin/main`, else `main`, else none: no commit checked). A seal commit is valid when its blob value or its patch value (`git patch-id --verbatim`, `seal`) matches (a clean rebase keeps the patch). A failed `git patch-id` gives no patch value: only the blob value counts. JSON `ok`, `violations` (`{reason, commit, path}`: `bad-seal` (plus `patch` `failed` when `git patch-id` failed for that commit: a git older than 2.39 or a broken git, not tampering; fix git and run it again), `unsealed`, `taint-unreadable` (the taint file cannot be read; `path`), `kit-changed` (a path under a kit skill folder, `.agents/skills/<name>/` of `dev-loop` and each `KIT_SKILLS` name of `lib/kit.mjs`, or `.dev-loop/`, or a `.dev-loop/MANIFEST.json` key at `<base>` or `HEAD`, differs from `<base>` and its content does not match the current MANIFEST entry (`sha256:` of the bytes, or `link:` target); fine: the MANIFEST itself, and a path gone from both the tree and the MANIFEST (an `upgrade` or `init` writes both); with `--uncommitted`, the working tree against `<base>`, untracked files under those folders too, `__pycache__/` and `*.pyc` skipped; `seal.sh` adds a kit remedy), `changed-after-seal` (both with `commits`: the non-seal commits that touched the path), `changed-before-seal` (`commit`: the seal commit, `path`, `commits` as above; see below), `uncommitted` only with `--uncommitted`: tracked changes, untracked paths only when named like a test file), `seal-dropped` (`commit`: the recorded sha, `paths`, `patch`: the newest recorded value; see below), `seal-record-unreadable` (the seal record cannot be read or has another shape; `path`)), `taint` (open records), `warnings` (closed records, audit skips, `seal-record-skipped` with `why`). A record in `taint` and `warnings` leaves out `lines` (held-out text: the audit would taint every implementer that runs `gate --summary`) and `paths` (held-out file names, kept out of the same output); `taint.json` keeps them. Exit 0 when `ok`, else 1; exit 2 outside a git repo.
- `changed-before-seal`: per path under `tests/acceptance/`, the expected blob is its blob at `<base>` (`deleted` when absent), moved only by each valid seal commit that touches the path (bad-seal and non-seal commits do not move it). A valid seal commit whose first parent holds another blob for a path it touches gives one violation per path. The seal commit stays valid: it still seals its paths. A non-seal commit and its revert, both before the seal commit, cancel. Remedy: rewrite the branch so that no non-seal commit before the seal commit changes the path: drop that commit (`git rebase --onto <sha from commits>^ <sha from commits>`: a sha from `commits`, never the seal commit in `commit`), or remove only its change to the path; a conflict under `tests/acceptance/` goes to `spec-tester` (`seal --rebase-continue`). A `git revert` does not clear it: the seal commit's parent still holds the change. `seal.sh` adds this remedy, as for `kit-changed`.
- `seal-dropped`: reads the seal record `<git-dir>/dev-loop/seals.json` (`seal`), only when `<base>` exists. Only the entries whose `branch` is `git symbolic-ref HEAD` count. An entry is present when a commit in the whole history of `HEAD` carries one of its `patches` values: the last paragraph of its message has the line `Dev-Loop-Seal-Patch: <value>` and a `Dev-Loop-Seal:` line too. A carrier commit counts for one entry only (each entry, in record order, takes one carrier not yet taken; a seal that re-adds the same content as an earlier one has the same value, so dropping it leaves the earlier carrier to the earlier entry alone); else one violation per entry, in record order. Only the trailer text counts: the carrier needs both trailer lines, and validity stays with `bad-seal` (a forged carrier in `<base>..HEAD` gets `bad-seal`; an amended seal commit gives `bad-seal`, not `seal-dropped`). No record file: no check (a fresh clone, CI, an older kit). The check is skipped, with the warning `seal-record-skipped` (`why`: `rebase`, `cherry-pick`, `detached`, in that order) and the file not read, during a rebase (`rebase-merge`, `rebase-apply`), with a `CHERRY_PICK_HEAD`, or on a detached `HEAD`. Remedy: `git cherry-pick <commit>`; on a conflict, `git cherry-pick --abort`, stop and report to the user. Only the user edits `seals.json`; `seal-record-unreadable`: stop and report, the user repairs or removes the file. `seal.sh` adds both remedies. Residuals: the shell can edit or remove `seals.json`, then a drop passes (the PR diff stays the backstop); a new worktree for the same branch starts with no record; a branch name used again in the same git dir inherits the old entries; a renamed branch leaves its entries unchecked.
- Residual: the patch value hashes the `-U1` diff, so added lines moved to a spot whose line before and line after are the same as the original ones keep the value (that spot must already exist on `main`).
- A rebase with `-X ours` or `-X theirs` that changes a neighbour line of the sealed lines gives `bad-seal`. Remedy: abort, rebase again without `-X`; a conflict goes to `spec-tester` (`seal --rebase-continue`).
